Status: **proof of concept** on branch `feat/008b-osm-map-poc` (issue #20). It implements the direction
the owner approved in METINAR-008 (`docs/METINAR-008-MAP-PROVIDER-SPIKE.md`): OSM vector tiles in the
OpenMapTiles schema, rendered by a MetinAR-owned Unity renderer, with OpenFreeMap as the prototype host.

## Architecture

```
PlayerLocationService ──fix──▶ PrototypeWorldPlacement ──captures once──▶ WorldMapOrigin (+X east, +Z north, 1u = 1m)
        ▲                                                                     │ read-only
 OsmPocBootstrap (Demo landmark | foreground GPS)                             ▼
                                         OsmMapView ── IMapTileSource (OpenFreeMapTileSource)
                                            │            └─ CachedHttpFetcher ─ DiskTileCache (LRU, 64 MB)
                                            │                   └─ ITileHttpTransport (UnityWebRequestTransport, main thread)
                                            ├─ Task.Run: OpenMapTilesDecoder(MvtReader) → MapFeature
                                            │           FeatureProjector (LocalTangentFrame == WorldMapOrigin math) → cull to 3×3 window
                                            │           MapMeshBuilder (Triangulator) → per-layer mesh data
                                            ├─ main thread: Mesh upload (one renderer per layer per source tile)
                                            └─ FeatureSpawnSafetyService  ──▶ ISpawnSafetyService (gameplay-facing)
```

* **Display zoom 16, radius 1** → 3×3 display tiles (≈1.2 km × 1.2 km at Polish latitudes); data comes
  from z14 ancestors (OpenFreeMap max zoom 14), normally 1–4 source tiles. Features are culled per
  line / polygon part to the window (no polygon clipping needed for rendering).
* **Origin contract**: `LocalTangentFrame` is a pure replica of `WorldMapOrigin.GetLocalMeters`
  (per-axis signed `GeoMath.DistanceMeters`); the smoke test asserts parity < 1e-6 m. The renderer never
  captures or moves the origin, so player / mob / NPC placement is the unchanged 004A code.
* **No provider leakage**: gameplay namespaces (`MetinAR.WorldMap`, `MetinAR.Location`, AR, UI) hold no
  `MetinAR.Map*` types, and `MetinAR.Map.Runtime` public API exposes no `MetinAR.Map.Osm` types
  (asserted by reflection in the smoke test). Swapping to self-hosted PMTiles or Mapbox means a new
  `IMapTileSource` / `IMapFeatureDecoder`, nothing else.
* **Threading**: `UnityWebRequest` is main-thread-only, so `UnityWebRequestTransport` posts each request
  to the captured Unity `SynchronizationContext`; decode / projection / meshing run on the thread pool;
  only `Mesh` creation runs on the main thread (timed as `uploadMs`).

### Rendering (P4)

Layers (each its own URP material in `MapStyleProfile`): landcover, landuse, park, water (polygons +
waterways), minor roads, major roads, paths, rail, buildings. Roads are flat ribbons with widths per
OpenMapTiles `class` (motorway 14 m … path 1.6 m) and bend joints; bridges are lifted slightly; tunnels
are dropped. Buildings are extruded from `render_height` / `render_min_height` (default 8 m, scaled ×0.6
and capped at 30 m for readability), `hide_3d` parts skipped. Flat layers use URP Simple Lit; buildings
use URP Lit; shadows off (mobile budget). Linear fog hides the window edge.

### Camera + attribution (P6)

`MapCameraRig` (new; the 004A `MapCameraFollow` is untouched): angled orbit follow, default pitch 50°,
distance 35 m. One-finger horizontal drag / J–L / left-mouse drag = yaw; two-finger pinch / scroll /
Z–X = zoom (12–80 m); two-finger vertical drag / I–K / right-mouse drag = pitch (30–75°).

Attribution is always visible bottom-right: the TileJSON attribution (`OpenFreeMap © OpenMapTiles Data
from OpenStreetMap`) plus `© OpenStreetMap contributors` (OSMF guideline wording). The (i) button opens a
panel with the credits, the ODbL note, the privacy note and a button to openstreetmap.org/copyright.

### Spawn safety (P7)

`ISpawnSafetyService.Evaluate(GeoCoordinate, clearanceMeters)` → `Allowed | Blocked(reason) | Unknown`;
`IsSpawnAllowed` is true **only** for `Allowed` (default-deny). `TryFindSafePoint` searches rings around
a point. Evaluation order: water / waterway → building → private (roads with `access=no`, restricted
landuse such as military, school, hospital, cemetery, industrial, construction…) → rail → road (buffer
by class) → known-surface check. Outside loaded coverage → `Unknown(NoData)`; inside coverage but on
no classified surface → `Unknown(UnclassifiedSurface)` while `RequireKnownSurface` (default true).

Prototype buffers (meters, `SpawnSafetyConfig`, all configurable): motorway 25, trunk 20, primary 15,
secondary 12, tertiary 10, minor 6, service 4, track 3, path 0, pedestrian 0, private road 6, rail 15,
water 5, waterway 6, building 2, restricted area 0. These are **not** a safety guarantee: OSM data is
incomplete, so the server-side spawn service must keep its own checks; this is a client-side filter.

## Privacy and network behaviour

* **The tile host sees the approximate area**: every tile request names a z14 tile (≈1.6 km × 1.6 km
  in Poland), so OpenFreeMap (served through Cloudflare's CDN) learns the approximate area the player is
  in plus the device IP address and the User-Agent `MetinAR/<version> (+https://github.com/mromanowski832-ctrl/MetinAR-2026)`.
  No account, API key, cookie, device id or telemetry is sent. Self-hosting PMTiles in production
  removes the third party.
* Foreground GPS only (existing `UnityLocationProvider` / `ForegroundLocationLifecycle`); no
  `ACCESS_BACKGROUND_LOCATION` (checked in the merged manifest, below).
* The POC scene sets `PlayerLocationService._diagnosticLogIntervalSeconds = 0`, so fixes are not
  logged; map code logs only aggregate counts / timings, never tile ids, URLs or coordinates (the smoke
  test scans all logs for coordinate / tile-URL patterns). Error messages are URL-sanitised.
* The Editor and the device **Demo** mode use a public landmark (west part of Rynek Główny, Kraków,
  `50.0614, 19.9362`), not anyone's location. On device the start panel asks for **Use my GPS** or
  **Demo: Kraków**.
* Disk cache: `Application.temporaryCachePath/MetinARMapTiles`, LRU-bounded to 64 MB, honours
  `Cache-Control` / `Expires` / `Age`, revalidates with `If-None-Match` / `If-Modified-Since`, falls
  back to stale data when offline. OpenFreeMap TOS respected: ≤ 4 parallel requests, unique UA, no bulk
  prefetch (only the visible neighbourhood is requested).

### Avatar smoothing (decision of Kierownik produkcji, PR #28, 2026-10-21)

Owner P8 GPS run: the map is OK, but the player **character** jumped from one GPS fix to the next
(`PlayerMapAvatar` moves the transform straight to the raw fix; there is no jitter filter in the GPS core).
Approved narrow fix, POC scene only:

- `Scripts/Map/Core/AvatarPositionSmoother.cs` (engine-free, `tests/MapCore.Tests/AvatarPositionSmootherTests.cs`):
  local east/north metres in, smoothed visual position out.
  - First fix: snap. Same timestamp: ignored (the provider is polled every frame). Older timestamp: ignored.
  - Jitter: moves below `max(2 m, min(6 m, 0.3 × accuracy))` do not move the target.
  - Outlier: implied speed > 8 m/s is held until the next fix confirms it (within 10 m). A non-confirming fix
    discards it; with no newer fix for 2 s it is accepted (mock/demo teleport).
  - Relock: ≥ 50 m after ≥ 10 s without an accepted fix snaps.
  - Visual: exponential approach (τ = 0.6 s), capped at 6 m/s, frame-rate independent.
- `Scripts/Map/Runtime/OsmPocAvatarSmoothing.cs` (order 90, LateUpdate, between `PlayerMapAvatar` and
  `MapCameraRig`): scene hierarchy is `Player` (raw GPS, gameplay: entity distances, map streaming) →
  `Visual` (smoothed; carries `Model` and is the camera target) → `Model`. `PlayerMapAvatar`,
  `WorldMapPrototype` and the GPS core are unchanged.
- Logging, dev builds only:
  - `[OsmPocAvatar] fix result=… dtFix=… stepM=… rawSpeed=… acc_m=… jitterThrM=… lagM=…` per new fix and a
    `summary` every 10 s (counts per result, max raw step, max visual per-frame step, max lag). Deltas,
    accuracy and timings only, never coordinates.
  - `PlayerLocationService._diagnosticLogIntervalSeconds = 2` in the POC scene. These `[PlayerLocationService]`
    lines contain absolute lat/lon: they stay in device logcat; never paste or commit them. GitHub reports
    use only `[OsmPocAvatar]` numbers.
- Smoke test: `avatar_smoothing_wiring`, `avatar_visual_converges_after_teleport`; the privacy check
  still rejects coordinates in every line except `[PlayerLocationService]`.
- Not in scope: spawn relocation (spawn safety stays diagnostic-only), the overlay overflow.
- Physical verification (walk outdoors in GPS mode on the A31): UNVERIFIED until run.
